SOLID Principles

Building Better Object-Oriented Code

🏗️

SOLID is an acronym for five design principles that make software more maintainable, flexible, and scalable. These principles help you write clean, robust code that stands the test of time.

S - Single Responsibility Principle
O - Open/Closed Principle
L - Liskov Substitution Principle
I - Interface Segregation Principle
D - Dependency Inversion Principle

S - Single Responsibility Principle

A class should have only one reason to change

❌ VIOLATION 
public class Employee {
    private String name;
    private double salary;
    
    // Business logic
    public void calculatePay() {
        // Calculate salary
    }
    
    // Database operations
    public void saveToDatabase() {
        // Save employee to DB
    }
    
    // Reporting
    public void generateReport() {
        // Generate employee report
    }
}
This class has THREE reasons to change: pay calculation logic, database schema changes, and report format changes. This violates SRP.
✅ SOLUTION 
public class Employee {
    private String name;
    private double salary;
    // Getters/Setters only
}

public class PayrollCalculator {
    public void calculatePay(Employee emp) {
        // Calculate salary
    }
}

public class EmployeeRepository {
    public void save(Employee emp) {
        // Save to DB
    }
}

public class EmployeeReporter {
    public void generateReport(Employee emp) {
        // Generate report
    }
}
Each class now has ONE clear responsibility and only one reason to change. This makes the code more maintainable and testable.

O - Open/Closed Principle

Open for extension, closed for modification

❌ VIOLATION 
public class AreaCalculator {
    public double calculateArea(Object shape) {
        if (shape instanceof Circle) {
            Circle circle = (Circle) shape;
            return Math.PI * circle.radius 
                   * circle.radius;
        } else if (shape instanceof Rectangle) {
            Rectangle rect = (Rectangle) shape;
            return rect.width * rect.height;
        }
        // Need to MODIFY this method
        // for each new shape!
        return 0;
    }
}
Adding a new shape (Triangle, Square, etc.) requires modifying existing code. This breaks the Open/Closed Principle and increases the risk of bugs.
✅ SOLUTION 
public interface Shape {
    double calculateArea();
}

public class Circle implements Shape {
    private double radius;
    
    public double calculateArea() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle implements Shape {
    private double width, height;
    
    public double calculateArea() {
        return width * height;
    }
}

public class Triangle implements Shape {
    private double base, height;
    
    public double calculateArea() {
        return 0.5 * base * height;
    }
}
Now you can add new shapes without modifying existing code! Just create a new class implementing Shape. The system is open for extension, closed for modification.

L - Liskov Substitution Principle

Subtypes must be substitutable for their base types

❌ VIOLATION 
public class Bird {
    public void fly() {
        System.out.println("Flying...");
    }
}

public class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException(
            "Penguins can't fly!"
        );
    }
}

// Usage problem:
Bird bird = new Penguin();
bird.fly(); // CRASH! 💥
Penguin breaks the contract of Bird. You cannot substitute a Penguin wherever a Bird is expected without unexpected behavior or exceptions.
✅ SOLUTION 
public abstract class Bird {
    public abstract void move();
}

public class FlyingBird extends Bird {
    public void move() {
        fly();
    }
    
    private void fly() {
        System.out.println("Flying...");
    }
}

public class Penguin extends Bird {
    public void move() {
        swim();
    }
    
    private void swim() {
        System.out.println("Swimming...");
    }
}

// Usage works perfectly:
Bird bird1 = new FlyingBird();
Bird bird2 = new Penguin();
bird1.move(); // Flying...
bird2.move(); // Swimming...
Both subtypes now correctly fulfill the Bird contract. You can substitute any Bird subtype without breaking the application.

I - Interface Segregation Principle

Clients shouldn't depend on interfaces they don't use

❌ VIOLATION 
public interface Worker {
    void work();
    void eat();
    void sleep();
}

public class HumanWorker implements Worker {
    public void work() { /* work */ }
    public void eat() { /* eat */ }
    public void sleep() { /* sleep */ }
}

public class RobotWorker implements Worker {
    public void work() { /* work */ }
    
    public void eat() {
        // Robots don't eat!
        throw new UnsupportedOperationException();
    }
    
    public void sleep() {
        // Robots don't sleep!
        throw new UnsupportedOperationException();
    }
}
RobotWorker is forced to implement methods it doesn't need. This creates a "fat interface" that doesn't make sense for all implementations.
✅ SOLUTION 
public interface Workable {
    void work();
}

public interface Eatable {
    void eat();
}

public interface Sleepable {
    void sleep();
}

public class HumanWorker 
    implements Workable, Eatable, Sleepable {
    public void work() { /* work */ }
    public void eat() { /* eat */ }
    public void sleep() { /* sleep */ }
}

public class RobotWorker implements Workable {
    public void work() { /* work */ }
    // No need to implement eat() or sleep()!
}
Classes now implement only the interfaces they actually need. This creates more flexible and maintainable code with smaller, focused interfaces.

D - Dependency Inversion Principle

Depend on abstractions, not concretions

❌ VIOLATION 
public class MySQLDatabase {
    public void save(String data) {
        System.out.println("Saving to MySQL");
    }
}

public class UserService {
    private MySQLDatabase database;
    
    public UserService() {
        // Tightly coupled to MySQL!
        this.database = new MySQLDatabase();
    }
    
    public void saveUser(String user) {
        database.save(user);
    }
}

// Cannot switch to PostgreSQL or MongoDB
// without changing UserService!
High-level UserService depends directly on low-level MySQLDatabase. This tight coupling makes it hard to test and impossible to switch databases.
✅ SOLUTION 
public interface Database {
    void save(String data);
}

public class MySQLDatabase implements Database {
    public void save(String data) {
        System.out.println("Saving to MySQL");
    }
}

public class MongoDatabase implements Database {
    public void save(String data) {
        System.out.println("Saving to MongoDB");
    }
}

public class UserService {
    private Database database;
    
    // Dependency injection!
    public UserService(Database database) {
        this.database = database;
    }
    
    public void saveUser(String user) {
        database.save(user);
    }
}

// Easy to switch databases:
UserService service = 
    new UserService(new MySQLDatabase());
UserService service2 = 
    new UserService(new MongoDatabase());
Now UserService depends on the Database abstraction. Easy to test with mocks, and you can swap implementations without changing UserService!

SOLID Recap

Why It Matters

S

Single Responsibility

One class, one job, one reason to change. Keep it focused and simple.

O

Open/Closed

Extend behavior without modifying existing code. Add features safely.

L

Liskov Substitution

Subtypes must be substitutable for base types. Maintain contracts.

I

Interface Segregation

Many specific interfaces beat one general interface. Stay lean.

Benefits of SOLID Principles

✅ Maintainable
✅ Testable
✅ Flexible
✅ Scalable

Follow these principles to write clean, professional code that's easy to understand, modify, and extend!
